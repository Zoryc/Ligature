# M4 — self-host polish

Two things for the people who run a Ligature server: a health check that sees real failures, and an
audit log page. (Moved to M5+ on 2026-11-19: password reset, gVisor, the CI-tested backup restore.)
Types: `packages/shared/src/api.ts`, section "self-host polish (M4)".

## 1. `GET /healthz`

Today `GET /api/health` answers `{ ok: true }` while the process runs, even when edits cannot be saved,
the collaboration socket is broken or the compiler is gone. `/healthz` checks the real paths.

- **Route:** `GET /healthz` and `HEAD /healthz` on the app server (outside `/api`, like the compiler's own
  `/healthz`). No login. `GET /api/health` stays as it is (plain liveness; existing monitors keep working).
- **Checks** (run in parallel, each with its own 2 s timeout; a timeout is `fail` with reason `timeout`):
  - `db` — `SELECT 1` on the server's connection and `db.open`. `fail` on an exception.
  - `disk` — free space of the data directory (`fs.statfs`): `fail` below 100 MB (reason `low-disk`),
    `warn` below 1 GB, else `ok`. `freeBytes` is reported. Where `statfs` is unavailable: `ok` without `freeBytes`.
  - `store` — the document store can persist edits: `fail` (reason `write-failed`) when its last flush of
    updates failed and no flush has succeeded since. Needs a small, tested hook in `DocStore`
    (remember the last flush error / last success); do not change how flushing works. One exception
    (review, 2026-11-19): the 200 ms batching timer, which usually writes a user's edits first, logs a failed
    write instead of throwing it; thrown from a timer it ended the process, so `write-failed` could never be
    reported. Direct callers of `flush()` still get the error.
  - `collab` — a real WebSocket upgrade on `/collab` over loopback (`ws` client to `127.0.0.1` or `::1`
    on the listening port, with an allowed `Origin`, no cookie). `ok` once the socket opens (101); then close
    it at once. Fail reasons: `timeout`, `refused`, `http-<status>` (e.g. a 403 when the origin list is wrong).
    The socket is closed immediately. It carries a per-process random token (header `x-ligature-health`,
    memory only), and the upgrade handler does not count it against the anonymous-socket cap (review,
    2026-11-19): anyone can hold that cap full, which must not make `/healthz` report the instance down.
    Origin, frame and byte limits still apply to it.
  - `compiler` — the compiler worker's own `/healthz` (existing `CompilerClient.health()`, 2 s): `fail`,
    reason `unreachable`. Skipped with `?scope=app`.
- **Answer:** `HealthReport`. HTTP **200** when no check is `fail` (status `ok`, or `degraded` with warnings),
  **503** when one is (status `down`). `Cache-Control: no-store`. Reasons are short codes only: never paths,
  hostnames, stack traces or messages from exceptions (the endpoint is public).
- **Abuse:** the result is cached for 5 s per scope, and concurrent requests share one run (single flight),
  so the public endpoint cannot be used to make the server open many sockets or call the compiler often.
- **Docker:** `docker/Dockerfile.app` HEALTHCHECK uses `/healthz?scope=app` (restarting the app would not fix
  a stopped compiler; the compiler container has its own HEALTHCHECK). docker/README.md: a short
  "Monitoring" section — point an uptime monitor at `https://<host>/healthz`; it checks the socket over
  loopback, so a reverse proxy that drops WebSocket upgrades is not detected by it (say how to check that:
  the editor shows "Offline", or `curl` with the upgrade headers through the proxy).
- **Tests (server):** healthy instance → 200 with every check `ok`; compiler pointed at a closed port → 503,
  `compiler: fail`, while `?scope=app` → 200; an origin list that rejects the loopback origin → `collab` fails
  with `http-403`; a forced store flush failure → `store: fail`, then ok again after a successful flush;
  cache: two calls within 5 s run the checks once; HEAD works; the body never contains the data path;
  a failed write by the batching timer → `store: fail` while the server stays up; a full anonymous-socket cap
  → `collab` still `ok`.

## 2. Audit log page

Every important action is already in `audit_log` (`apps/server/src/audit.ts`). Admins get a page to read it.

- **API:** `GET /api/admin/audit` (admin only, like the other `/api/admin/*` routes) → `AuditPage`.
  - Query: `limit` (1–200, default 100), `before` (entry id; keyset pagination on `id DESC`), `category`
    (one of `AUDIT_CATEGORIES`), `actor` (user id), `project` (project id, also deleted or purged ones),
    `since` / `until` (ms). Invalid values → `400 bad-request` (zod, like the other routes).
  - Each entry: `AuditEntryView`. `actor` is `null` only when `actor_id` is NULL (server, CLI). An actor id
    with no account row (should not happen: accounts are disabled, not deleted) gives
    `{ id, username: '', displayName: '' }`, which the client shows as "a deleted account". `project.name` comes from `projects` (soft-deleted ones too, `deleted: true`);
    a purged project has `name: ''` unless `detail.name` holds it. `users` holds every account named by
    `detail.userId`, and `detail.from` / `detail.to` of `ownership-transfer`.
  - `detail` is returned as stored. Audit entries never contain secrets (`audit()` contract); keep it so.
  - Migration 6: `CREATE INDEX audit_log_actor ON audit_log(actor_id, id)` (the actor filter).
  - Reading the audit log is not itself audited (it would flood the log).
- **Web:** the Admin page gets tabs — **Users** (registration, users, create user: as today), **Storage**
  (the StorageSection), **Audit log** — reachable as `#/admin`, `#/admin/storage`, `#/admin/audit`
  (`routes.ts`, with tests). The audit tab, in Folio style:
  - Filter bar: category select ("All activity", "Accounts and sign-in", "Administration", "Members and
    invites", "Projects and files", "History"), person select (from `/api/admin/users`), period select
    (last 24 h, 7 days, 30 days, all). A project filter appears as a removable chip after clicking a project
    name in a row; clicking a person's name sets the person filter.
  - Rows, newest first: time (date + time; tabular figures; full timestamp in the title), who (square
    Avatar + name, or "Server" for `actor: null`), what — one plain sentence, e.g. "changed the compiler of
    *Demo paper* from pdfLaTeX to XeLaTeX", "failed to log in as *bob* (wrong password)", "restored *Demo
    paper* to “Draft 1”" — and the project as a link-styled button (filter). Failed logins and deletions
    carry a red mark. A row can be expanded to show the recorded details (monospace key/value list).
  - "Load older" at the end (uses `next`); "No activity matches these filters." when empty; errors in the
    usual way. Times are local.
  - The sentences come from a pure, tested `apps/web/src/lib/auditText.ts`: one test per known action, and
    unknown actions fall back to the action name.
- **Tests (server):** admin only (403 for a non-admin, 401 without login); newest first and keyset
  pagination without gaps or repeats; every filter, and filters combined; deleted project → `deleted: true`;
  `users` resolution; limit bounds and bad input → 400; the index exists after migration 6.
